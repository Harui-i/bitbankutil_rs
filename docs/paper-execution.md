# paper tradingの約定モデルと時計

`PaperExecutionEngine::new(config, clock, balances, recorder)` で時計を明示します。
paper tradingでは `PaperClock::Realtime`、backtestでは `PaperClock::Replay { now_ms: 0 }` を選びます。
レコーダーは任意であり、記録用のtask-local contextも約定判定には使いません。

`Realtime` は操作・受信時にシステムのUTC Unixミリ秒を読みます。
`Replay` は指定した時刻だけを使い、実行マシンの現在時刻や処理速度を参照しません。
`BotRunner::process` / `advance_time` は `TradingVenue::advance_replay_time` を通じて時計を更新します。
エンジンやvenueを直接使う場合は、入力・注文操作の前に `advance_replay_time(time_ms)` を呼びます。
再生時計の初期値は最初の入力時刻以下にします。再生時刻の逆行と実時計の更新は `InvalidClock` エラーになります。

## 固定オフセットと時計の所属

`config.time_model = PaperTimeModel::FixedOffset { exchange_minus_local_ms: delta }` で、
対応する取引所時刻 **E = ローカル時刻 L + δ** を設定します。単位は符号付きi64の整数msです。
既定値はδ=0です。これは同期済みという確認ではなく、利用者が選ぶ仮定です。
時計差の自動推定や時間変動するドリフトは扱いません。受信時刻と取引所時刻の差だけから、
時計差と通信遅延を一意に分離することもできません。

| 時刻 | 所属・扱い |
| --- | --- |
| 生記録の received_at_micros | ローカルUTC Unix us。書き換えず受信順に使う |
| ctx.now_ms()、記録の event_time_ms | ローカル実行時計。入力受信時はusをmsへ切り捨て、API待機中の内部期限・滞留配送では進んだ現在時刻を使う |
| PaperClock、操作時の時計読み取り | ローカルUTC Unix ms。比較境界で一度だけEへ変換 |
| 板のlast_timestamp()、公開約定のexecuted_at | 取引所UTC Unix ms。変更しない |
| 注文有効開始・取消有効時刻、過去の操作下限、watermark | 取引所UTC Unix ms。δを再適用しない |
| recorded_at_ms | 記録を書き出したローカル実時計。backtestの約定判定には使わない |

usでの入力順はms変換後も維持します。同msの複数操作・入力を許し、ms内の順序を
取引所の成立順序とはみなしません。注文有効期間の境界は下記の開区間です。
設定は実行中に変更できません。`PaperExecutionConfig.time_model` と `PaperSettlementStatus.time_model` に
モデル名とδを残します。記録時は `paper_initial_state.config`、`paper_settlement`、
`replay_outcome.settlement` から識別できます。レコーダーなしでも設定と結果に残ります。

全i64オフセットを許しますが、初期化と再生時計の更新でL+δを検証し、範囲外なら
`InvalidClock` を返して時計・資金を変更しません。実時計の読み取りや変換が範囲外の場合も
発注は資金拘束前に失敗します。戻り値のない取消・市場登録ではissuesを記録して確定を停止します。
自動watermarkの減算もchecked演算とし、範囲外では飽和やラップをせずissuesに残します。
負のUnix時刻も表現できます。負の遅延上限は `InvalidWatermark` です。

`Realtime` のUTCが逆行しても過去の操作・板・watermarkの下限を維持し、操作有効時刻は逆行させません。
自動watermarkも後退させず、新しい計算境界が既存境界へ追いつくまで待ちます。
前方へのUTC補正で遅延仮定が破られる可能性は残ります。`Replay` は逆行入力を拒否し、
再生入力の検証はmsへの切り捨て前にus精度でも逆行を検出します。

## 発注・取消の遅延とローカルの認識

エンジンは取引所側の約定・残高を管理します。通常の戦略は `PaperTradingVenue` 経由で操作し、
ローカルへ届いた応答・通知に基づく口座状態を参照します。`venue.engine()` は診断用の取引所状態であり、
戦略が直接読めば未通知の情報を参照することになります。直接変更も通知経路を迂回するため避けてください。

```rust,ignore
let venue = PaperTradingVenue::with_latency(engine, PaperLatencyConfig {
    placement: PaperOperationLatency { entry_ms: 50, response_ms: 50 },
    cancellation: PaperOperationLatency { entry_ms: 150, response_ms: 50 },
    orders_query: PaperOperationLatency { entry_ms: 20, response_ms: 40 },
    balances_query: PaperOperationLatency { entry_ms: 40, response_ms: 40 },
    notification_ms: 20,
})?;
```

上記の値は説明用の仮定です。API全体の実測時間を半分にして片道の実測値とみなしてはいけません。
`PaperTradingVenue::new` は全遅延0を選ぶ同じ状態機械です。すべて非負の整数msで、時刻加算や
取引所時計への変換が範囲外なら要求を登録する前に失敗します。時計差δ、公開約定の到着上限、
注文操作の遅延は独立した設定です。

| 出来事 | 時刻・意味 |
| --- | --- |
| 要求送信 | ローカルL。Futureが最初にpollされたときに要求を登録 |
| 新規注文有効化 | L + placement.entry_ms、取引所時計ではこの値 + δ。ここで資金を判定・拘束 |
| 発注応答 | 有効化後 placement.response_ms。受付または拒否をローカルへ通知 |
| 取消有効化 | L + cancellation.entry_ms。それまで旧注文は約定し得る |
| 取消応答 | 有効化後 cancellation.response_ms。成功は取消受付ackで、残数量・資金の確定保証ではない |
| 約定・取消確定の通知 | watermarkで確定可能になったローカル時刻 + notification_ms以降 |

実時計のタイマー処理が遅れた場合は実行できた時刻で有効化し、過去へ遡って受付・通知しません。
ローカル口座の状態通知は取引所状態遷移の順序を保つスナップショット列です。先行する未通知の受付があると、
後続の口座通知もその時刻以降まで待ちます。これは口座状態の一貫したprefixを公開するための明示的な簡略化です。
REST応答の完了順と口座通知の公開順は別で、遅い先行通知により後続の口座反映が遅れることがあります。
この通知用キャッシュは `known_account_snapshot()` で読み出せます。REST照会の
`account_snapshot()` は以下の別経路を使い、キャッシュへ照会結果を書き戻しません。

### 注文一覧・残高の照会

`PaperLatencyConfig.orders_query` / `balances_query` にそれぞれ
`PaperOperationLatency { entry_ms, response_ms }` を設定します。`entry_ms` は要求から
取引所で採取するまで、`response_ms` は実際の採取からローカル応答までの非負整数msです。
既定は0です。実APIと同じく2照会を並行開始し、両応答がそろってから
`account_snapshot()` が返ります。片方が失敗しても、他方の送信済み要求を消しません。

採取時点でエンジンが把握している注文一覧・残高をそれぞれ凍結し、応答時に最新状態へ
差し替えません。両採取時刻は異なり得るため、返却値は原子的な口座snapshotではありません。
注文応答や非同期通知より先に、照会から取引所で受付済みの注文を知ることもあります。
古い照会結果は呼び出し元へ返すだけで、通知用キャッシュを巻き戻しません。

返却値の `AccountSnapshot.query` は、各照会の要求ID、ローカル要求・採取・応答時刻、
取引所採取時刻、採取時点のwatermark・`unsettled`・`issues` を保持します。
採取イベントの記録では `received_local_ms` はまだNone、応答後の返却値ではSomeです。
合成完了時刻も別に残します。実APIではサーバー内の採取時刻が分からないため、queryはNoneです。

公開約定の通知が遅れている間、採取時点の真の取引所口座を再現できるとは保証しません。
採取時点で既知の状態を返す簡略化であり、未確定ならmetadataも未確定のままです。
後から届いた取引で返却済みsnapshotを書き換えず、未来情報を先に登録して確定もしません。
未確定な採取値を応答した件数を `settlement_status().uncertain_query_observations` に累積し、
後のwatermarkが追いついてもその評価の `unsettled` を解除しません。この履歴を含む評価を
無条件に確定した損益として扱わないでください。件数は端点ごとの応答数で、実際に戦略が
値を使用したかまでは判定しません。キャッシュの即時読出しを実取引所照会とは扱いません。

`paper_query_requested` / `paper_query_sampled` / `paper_query_response` /
`paper_query_completed` を既存の実行記録へ保存します。記録無効でも同じ状態遷移です。
待機中も市場・注文処理は進みますが、同一戦略の次のハンドラーは逐次配送されます。
paperのタイマーが遅れた場合は実際の採取時刻から応答遅延を数え、過去へ遡りません。
EOFや評価境界では未採取・未応答の照会を保留し、既存の残存操作一覧へ残します。

送信中の要求に対するローカルでの資金予約は行いません。取引所の資金判定は有効化順に直列化するので、
同じ資金を見て送った競合要求は一方が拒否され得ます。失敗も発注応答の期限で返り、二重拘束は行いません。
同一注文の重複取消は1回の取消として扱い、既に全約定した注文への取消ackでも資金を二重解放しません。
別々の発注要求は別注文であり、自動的な冪等化はしません。

十分な資金がある並行差し替えでは、新注文の有効化から旧注文の取消有効化まで両方が約定対象になります。
既存のorder_managerは操作Futureを同じタスクで並行pollし、登録順をOS/Tokioの子タスク起床順に依存させません。
利用者が独立したタスクから競合要求を出す場合、その登録順まで決定的になるとは保証しません。

backtestではvenueの内部期限と次の市場受信時刻を比較し、戦略Futureが注文応答をawait中でも市場をvenueへ登録します。
戦略へのイベント配送はハンドラーが完了するまで保留します。受信済み入力の時刻を飛び越えてから巻き戻す方法は使いません。
実時間のsleepは不要です。paperでは同じ状態機械を実時計のタイマーで駆動し、市場入力がなくても操作期限を進めます。

要求Futureをdropしても、既に送信した要求を取り消したことにはなりません。未応答の操作は
`pending_operations()` と確定状態の `pending_operation_details` に残ります。
`pending_operations` 件数には未配信の口座通知も含みます。EOF・評価終了・中断で強制完了せず、結果に保留を残します。
切断・評価異常時は新規受付・約定確定の既存制限を維持し、再接続だけでは正常扱いへ戻しません。

`paper_latency_model`、`paper_operation_requested`、`paper_operation_effective`、
`paper_operation_response`、`paper_local_state` を既存レコーダーへ保存します。
予定時刻と実行時刻、ローカル時計と取引所時計を区別し、元の操作・入力コンテキストを引き継ぎます。
確定状態にも遅延設定と残存操作を保存するため、記録を無効にしても条件と未完了を識別できます。

## 注文の有効期間と通知

- 受信時刻は市場データがローカルへ届いた時刻です。backtestでは記録の `received_at_micros` です。
- 戦略の実行時刻は `ctx.now_ms()` です。paper tradingでは実時計、backtestでは現在のローカル仮想時計です。受信時刻をmsへ切り捨てて時計を進め、API待機・滞留配送中はさらに進み得ます。派生イベントも配送時の現在時計を使い、元入力の識別子は別に引き継ぎます。
- 取引所時刻は板の `last_timestamp()` や公開約定の `executed_at` です。
- 有効開始時刻は取引所時計へ変換した受付時計、観測済みの対象pairの板時刻、過去の操作時刻、確定済み境界の最大値です。`OrderAccepted.effective_after_ms` に保存します。
- 取消有効時刻も同じ時計と下限で求め、既に封鎖したwatermarkの次のms以降にします。エンジンへの取消適用時に有効化します。venueでは要求から設定した遅延後に適用します。残数量と資金解放は確定境界まで待ちます。

公開約定は `effective_after_ms < executed_at < cancel_at_ms` の注文だけを執行します。
取消されていない注文には終了境界がありません。ms内の前後関係は不明なので、開始・取消と同じmsの取引は対象外です。
部分約定でも開始時刻は変えません。同価格の差し替えにも別の有効期間を割り当てます。

例えば、1000msに売り注文A、1200msに取消、1250msに売り注文Bを受け付け、
1400msに成立時刻1100msの買い約定を受信した場合、確定時にAを約定させます。
Bには付け替えません。取消の受付を表す `OrderCancelPending` の後もAの未確定数量分の資金を拘束し、
約定・手数料を反映してから `OrderCancelled.order.remaining_amount` 分だけ解放します。
全約定なら取消残数量は0です。`cancel_orders` の成功は取消受付を表します。

エンジンの `open_orders()` は取消有効化済み注文を除きますが、その拘束資金は `balances()` に残ります。venueのローカル口座へは応答・通知の公開後に反映します。
その資金を使う次の注文は、取消確定まで資金不足で拒否されます。取消受付を待って即座に全額を差し替える戦略は、
確定後の残高で再計画してください。約定による入金も確定時まで発注に使えません。

## 公開約定の完了境界（watermark）

既定の `apply_market_event` / `on_market_event` は公開約定を登録するだけで、資金を動かしません。
`advance_trade_watermark(through_ms)` により「成立時刻がthrough_ms以下の取引はすべて受信済み」と保証します。
`PaperTradingVenue` にも同名のメソッドがあります。この呼び出し時に、登録済み取引を成立時刻順、同msではtransaction ID順に処理し、
続いて境界内の取消残数量を解放します。戻り値と `drain_events()` から約定・取消確定を取得できます。

境界は単調に進めます。新注文・取消を確定済み時刻より前へ挿入できません。
同じmsでも既に境界を封鎖した後の取消は、次の未確定ms以降に有効になります。
このため境界を封鎖した後で、同msに既に確定した部分約定を遡って消すこともありません。
同一ID・同一内容の再通知は無視します。IDの内容衝突、不正数量・価格、境界以下への未知の遅着は評価異常として残します。
その後は新規注文・約定確定・資金解放を停止します。取消受付は可能ですが資金は保留します。
エンジン直接利用時は `settlement_status().issues` を確認します。
venueの通常入力経路では `InvalidTradeStream` エラーも返しますが、復旧経路では市場入力の登録・配送を継続します。
どちらも新規注文と明示的な確定操作は `InvalidTradeStream` で拒否します。

板の時刻、別チャネルの進行、単なるファイルEOF、再接続は、公開約定の完了証明にはなりません。
backtestでも全入力を取引所時刻で並べ替えず、戦略へは受信順で市場情報を渡します。
内部の確定処理だけ成立時刻順にします。完了境界もその時点で利用可能な根拠に基づいて供給し、
未来の受信データを先に登録したり、その内容から戦略に有利な境界を選んだりしないでください。

### 遅延上限を仮定する場合

利用側が上限を選ぶ場合だけ `engine.with_max_trade_delay_ms(delay)` を設定できます。
市場イベントを取り込んだ後、**L(receipt) + δ - delay - 1ms**を取引所時計の境界として自動確定します。
取引所時計へ変換した受信時刻と成立時刻の差がdelayちょうどなら許容し、delayより大きければ上限超過です。
これは取引所が保証する値ではありません。無制限の遅延や欠損を有限の待機で解決できるとはしません。
設定値とモデルはレコーダーに記録されます。遅延上限を超える未知の取引が届いた場合も異常を記録し、確定を停止します。
δと公開約定の遅延上限は独立の設定です。発注・取消の有効化遅延ではありません。
過去の確定済み計算を巻き戻して正常扱いには戻しません。

`best_mm --paper ... BASE_INITIAL JPY_INITIAL MAX_TRADE_DELAY_MS` はこの仮定を明示的に使う例です。
WebSocket依存層は通信エラー・サーバー切断後に自動再接続し、設定された間隔で接続を再試行します。
paperランタイムは再接続後に届く市場情報を同じ戦略へ渡します。
ただし現在の接続ラッパーは内部の再接続・全欠損をvenueへ通知しないため、接続の連続性は検証できません。
この経路の評価はその仮定付きです。欠損が観測できる独自入力では `mark_market_incomplete(reason)` を呼んでください。
遅着が一度もなくても、未観測の欠損がない証明にはなりません。

## 終了・切断と記録

口座照会は `settlement_observation()` でwatermark、現在の未確定性、異常理由の参照だけを取得します。
キュー履歴の長さによらず割当なしで取得でき、採取metadataへ保存するときだけ異常理由を
settlement issues、model issuesの順にコピーします。過去の未確定照会の累積は現在の採取値には含めません。
ランナーの保留判定は `TradingVenue::has_pending_operations()` を使い、キューや操作詳細を複製しません。

`settlement_status()`（venueの共通APIでは `paper_settlement_status()`）は境界、仮定した遅延上限、
保留中の取引・取消件数、未確定フラグ `unsettled`、異常理由 `issues` を返します。
現在の操作・評価時刻まで境界が到達していない末尾も未確定です。終了時に必ず結果と一緒に保存し、
未確定残高を正常に確定した損益へ混ぜないでください。全注文取消だけでは終了確定になりません。

切断・欠損・中断時は `mark_incomplete`（venueでは `mark_market_incomplete`）で異常を保存します。
再接続や板復元だけでは解除しません。`run_replay` は切断・入力エラー・中断を自動で伝え、
終了時に `ReplayReport.settlement` を保存します。未確定なら `incomplete` もtrueです。
`run_replay(..., recovery: true, ...)` と通常のpaperランタイムは、未確定状態のままでも
市場入力と戦略の実行を継続できます。記録形式・入力変換の検証や戦略のエラーを握りつぶすものではありません。
戦略自身が発注拒否をエラーとして返せば戦略は終了します。執行を再開するには欠損を埋めて
注文・残高の整合性を回復する仕組みが必要であり、現在のエンジンにはその自動復旧APIはありません。
保証できる境界がない終了では強制flushせず、拘束資金と未確定注文を保留したまま結果を残します。
合成fixtureなどで完了範囲が既知の場合だけ、明示的に境界を供給してから終了します。

通常ランタイムの正常shutdown・処理失敗時にも確定状態をログとレコーダーへ保存します。Dropによる強制停止では保証しません。
レコーダーは `paper_settlement`、`paper_delay_assumption`、`paper_event` を保存します。
約定の成立時刻・取引IDは `OrderFilled.trade` に残り、確定時刻とローカル通知時刻は `paper_event` と `paper_local_state` で区別します。
明示的な境界をランナー外で供給するとき、入力に由来する境界なら記録コンテキストも呼び出し元で接続してください。
IDの重複検出履歴と未確定取引は、正確性のため期間中保持します。長期運用ではメモリ量も監視し、
未確定状態を捨てて正常終了に見せるローテーションはしないでください。

## 観測板による受付と先行数量

執行モデルは `observed_book_fifo_v1` です。注文が有効化する時点で、そのときまでに受信した
対象pairの最新の有効なL2板を使います。これは受付時の真の取引所板を再構成するものではなく、
**観測板に基づく近似**です。戦略が発注を決めた時点の板を固定して受付判定することもしません。
板の取引所時刻とローカル観測時刻、最良価格・可視範囲を `PaperBookEvidence` に保持し、
受付記録には有効時刻との差 `book_age_ms` を残します。古い取引所時刻の後着snapshotで
新しい観測板を巻き戻しません。後着の板を、未受信の時点の戦略へ先渡しもしません。
板の鮮度は記録するだけで、遅延のない真の板を保証する閾値ではありません。

板は初期化済みで両sideがあり、正の価格と有限・正の数量、best bid < best askを必要とします。
買い価格が最下位の可視bidより低い場合、売り価格が最上位の可視askより高い場合は、
先行数量が不明なので受付できません。可視範囲内の価格に表示数量がない場合は0と扱います。
板なし・不正板・可視範囲外などは `ExecutionModelUnavailable` で拒否し、
先行数量0の成功注文には変換しません。モデルの不足は `model_issues` に残り、
後の正常な板で受付できても、既に不確かな評価だった履歴を正常損益へ戻しません。
切断・欠損の既存の執行停止も、再接続や新snapshotだけでは解除しません。

### post-onlyと未対応の注文

Normal modeでは、買い価格 >= best ask、売り価格 <= best bidのpost-only注文は、
同値や一部数量の対当も含め**注文全体を板へ残しません**。
取引所のpost-onlyによる取消に対応する模擬APIの表現は
`PaperRejectReason::PostOnlyWouldTakeLiquidity` です。注文IDを発行せず、資金拘束前に拒否し、
PR4の応答遅延後に呼び出し元へ失敗を返します。受付後のopen_ordersや取消待ち資金を作りません。
post-onlyなしのcross注文もmakerとして扱わず、taker未実装の `UnsupportedTaker` として拒否します。

`config.assume_normal_mode` は既定trueです。これはNormal modeを仮定する設定で、
取引モードの観測済み保証ではありません。falseなら対象pairの `CircuitBreakInfo.mode == "NONE"`
を受け取るまで受付できません。モードを観測した場合はその値を優先します。
Normal以外ではpost-only保証が無効になるため、当モデルは `UnsupportedMarketMode` として扱い、
そのモードでの注文執行を正常なmaker損益には含めません。

### 同価格の共有FIFO

同価格の最初の自注文は、観測した表示数量の後ろへ入ります。同価格の外部先行数量と
自注文を、価格レベルで共有するFIFO列に保持します。後から有効化する自注文は末尾へ入るため、
外部先行数量を各自注文へ重複して計上しません。部分約定は順位を継続し、取消・再発注は新規の順位です。
追跡済み価格レベルは自注文がゼロになっても保持し、その間の公開約定も外部数量へ反映します。
消化済みの数量を古い観測板から復活させず、後続注文は同じ列を引き継ぎます。
このレベル履歴も実行期間中は保持するため、長期評価では約定ID履歴と同様にメモリ量を監視してください。

同価格の公開約定は、列の外部数量を消化し、その超過分だけを自注文へ割り当てます。
例えば表示先行数量10・自注文3に対する公開数量6、5、2なら、自注文の約定は0、1、2です。
板数量の減少からは先頭数量を減らしません。減少が約定か取消かを推定して有利に繰り上げず、
公開約定とdepth減少によって同じ数量を二重に消化することを防ぎます。
観測数量の増加は既存自注文の後ろへ追加し、その観測より前に成立した約定で消化しません。

価格を明確に通過した公開約定は、より良い価格の外部先行数量を通過済みとして扱う近似です。
その場合も自分の合計約定数量は当該公開約定数量を上限とし、価格優先、同価格は列の順序で
割り当てます。注文有効前・取消有効後の取引は自注文へ割り当てず、有効化前の取引で新しい
先行数量を減らしません。代金とmaker手数料は注文価格で計算し、既存の資金拘束・確定処理を使います。

`settlement_status()` には `execution_model`、`book`、`queue`、`model_issues` を残します。
記録では `paper_queue_admission` / `paper_queue_book` / `paper_queue_trade` に受付根拠と列の変化を残し、
レコーダーがなくても同じモデル・数量で処理します。公開約定watermarkは板チャネルの完了保証には使いません。

このモデルはL2の表示数量による推定です。実際の注文単位の順位、非表示数量、市場インパクト、
自分の注文による他者の行動変化は再現しません。約定しにくい近似にすれば損益が必ず保守的に
なるとは限りません。固定時計差・固定遅延も仮定であり、実測分布の校正は別の作業です。
任意の非同期タスクやTokioタイマーの全般的な仮想化も行いません。

post-onlyの取引所仕様は [bitbank公式説明](https://support.bitbank.cc/hc/en-us/articles/900005145623-What-is-PostOnly)、
APIの項目は [REST API仕様](https://github.com/bitbankinc/bitbank-api-docs/blob/master/rest-api.md)を参照してください。

`tests/paper_settlement.rs` は固定の注文操作・開始残高に対し、通知遅延と順序だけを変え、
約定数量・代金・手数料・評価損益・共通の約定後価格列での値動きを比較します。
これは合成時系列による回帰検証です。実履歴での性能やpaper tradingの発生頻度の実測ではありません。

長期backtestでのqueueの保持量、診断API、履歴整理の条件と合成benchmarkは
[長期backtestのqueue履歴](queue-history.md)を参照してください。

### 照会のキュー履歴コストの検証

`cargo test --locked --test settlement_cost -- --nocapture` で、1価格レベルの外部数量増加を
10 / 1,000 / 10,000回与え、履歴を保持したまま各処理を100回計測できます。
割当数・要求bytes・経過時間を出力し、軽量metadataとpending判定が割当なしであること、
記録なしの口座照会全体の割当数・bytesが履歴量によらないことを検証します。
比較対象は従来の採取経路が使っていた詳細診断です。詳細診断の完全なsegment数も確認します。
時間は実行環境に依存するため合否の基準には使いません。
