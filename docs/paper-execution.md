# paper tradingの約定モデルと時計

`PaperExecutionEngine::new(config, clock, balances, recorder)` で時計を明示します。
paper tradingでは `PaperClock::Realtime`、backtestでは `PaperClock::Replay { now_ms: 0 }` を選びます。
レコーダーは任意であり、記録用のtask-local contextも約定判定には使いません。

`Realtime` は操作・受信時にシステムのUTC Unixミリ秒を読みます。
`Replay` は指定した時刻だけを使い、実行マシンの現在時刻や処理速度を参照しません。
`BotRunner::process` / `advance_time` は `TradingVenue::advance_replay_time` を通じて時計を更新します。
エンジンやvenueを直接使う場合は、入力・注文操作の前に `advance_replay_time(time_ms)` を呼びます。
再生時計の初期値は最初の入力時刻以下にします。再生時刻の逆行と実時計の更新は `InvalidClock` エラーになります。

## 注文の有効期間と通知

- 受信時刻は市場データがローカルへ届いた時刻です。backtestでは記録の `received_at_micros` です。
- 戦略の実行時刻は `ctx.now_ms()` です。paper tradingでは実時計、backtestでは受信時刻をmsへ切り捨てた時計です。派生イベントでも同じ時刻を使います。
- 取引所時刻は板の `last_timestamp()` や公開約定の `executed_at` です。ローカル時計と同じUTC epochを仮定します。
- 有効開始時刻は受付時計、観測済みの対象pairの板時刻、過去の操作時刻、確定済み境界の最大値です。`OrderAccepted.effective_after_ms` に保存します。
- 取消有効時刻も同じ時計と下限で求め、既に封鎖したwatermarkの次のms以降にします。取消は即時有効とする簡略化ですが、結果通知と資金解放は確定境界まで待ちます。

公開約定は `effective_after_ms < executed_at < cancel_at_ms` の注文だけを執行します。
取消されていない注文には終了境界がありません。ms内の前後関係は不明なので、開始・取消と同じmsの取引は対象外です。
部分約定でも開始時刻は変えません。同価格の差し替えにも別の有効期間を割り当てます。

例えば、1000msに売り注文A、1200msに取消、1250msに売り注文Bを受け付け、
1400msに成立時刻1100msの買い約定を受信した場合、確定時にAを約定させます。
Bには付け替えません。取消の受付を表す `OrderCancelPending` の後もAの未確定数量分の資金を拘束し、
約定・手数料を反映してから `OrderCancelled.order.remaining_amount` 分だけ解放します。
全約定なら取消残数量は0です。`cancel_orders` の成功は取消受付を表します。

`open_orders()` は取消受付済み注文を除きますが、その拘束資金は `balances()` に残ります。
その資金を使う次の注文は、取消確定まで資金不足で拒否されます。取消受付を待って即座に全額を差し替える戦略は、
確定後の残高で再計画してください。約定による入金も確定時まで発注に使えません。

## 公開約定の完了境界（watermark）

既定の `apply_market_event` / `on_market_event` は公開約定を登録するだけで、資金を動かしません。
`advance_trade_watermark(through_ms)` により「成立時刻がthrough_ms以下の取引はすべて受信済み」と保証します。
`PaperTradingVenue` にも同名のメソッドがあります。この呼び出し時に、登録済み取引を成立時刻順、同msではtransaction ID順に処理し、
続いて境界内の取消残数量を解放します。戻り値と `drain_events()` から約定・取消確定を取得できます。

境界は単調に進めます。新注文・取消を確定済み時刻より前へ挿入できません。
同じmsでも既に境界を封鎖した後の取消は、次の未確定ms以降に有効になります。
このため境界を封鎖した後で、同msに既に確定した部分約定を遡って消すこともありません。
同一ID・同一内容の再通知は無視します。IDの内容衝突、不正数量・価格、境界以下への未知の遅着は評価異常として残します。
その後は新規注文・約定確定・資金解放を停止します。取消受付は可能ですが資金は保留します。
エンジン直接利用時は `settlement_status().issues` を確認し、venue経由では `InvalidTradeStream` エラーも受け取ります。

板の時刻、別チャネルの進行、単なるファイルEOF、再接続は、公開約定の完了証明にはなりません。
backtestでも全入力を取引所時刻で並べ替えず、戦略へは受信順で市場情報を渡します。
内部の確定処理だけ成立時刻順にします。完了境界もその時点で利用可能な根拠に基づいて供給し、
未来の受信データを先に登録したり、その内容から戦略に有利な境界を選んだりしないでください。

### 遅延上限を仮定する場合

利用側が上限を選ぶ場合だけ `engine.with_max_trade_delay_ms(delay)` を設定できます。
市場イベントを取り込んだ後、受信時計 - delay - 1msを境界として自動確定します。
これは取引所が保証する値ではありません。無制限の遅延や欠損を有限の待機で解決できるとはしません。
設定値とモデルはレコーダーに記録されます。遅延上限を超える未知の取引が届いた場合も異常を記録し、確定を停止します。
時計差も上限の仮定に含める必要があります。過去の確定済み計算を巻き戻して正常扱いには戻しません。

`best_mm --paper ... BASE_INITIAL JPY_INITIAL MAX_TRADE_DELAY_MS` はこの仮定を明示的に使う例です。
現在のWebSocket依存層は内部の再接続・全欠損をこのライブラリへ通知しないため、接続の連続性は検証できません。
この経路の評価はその仮定付きです。欠損が観測できる独自入力では `mark_market_incomplete(reason)` を呼んでください。
遅着が一度もなくても、未観測の欠損がない証明にはなりません。

## 終了・切断と記録

`settlement_status()`（venueの共通APIでは `paper_settlement_status()`）は境界、仮定した遅延上限、
保留中の取引・取消件数、未確定フラグ `unsettled`、異常理由 `issues` を返します。
現在の操作・評価時刻まで境界が到達していない末尾も未確定です。終了時に必ず結果と一緒に保存し、
未確定残高を正常に確定した損益へ混ぜないでください。全注文取消だけでは終了確定になりません。

切断・欠損・中断時は `mark_incomplete`（venueでは `mark_market_incomplete`）で異常を保存します。
再接続や板復元だけでは解除しません。`run_replay` は切断・入力エラー・中断を自動で伝え、
終了時に `ReplayReport.settlement` を保存します。未確定なら `incomplete` もtrueです。
保証できる境界がない終了では強制flushせず、拘束資金と未確定注文を保留したまま結果を残します。
合成fixtureなどで完了範囲が既知の場合だけ、明示的に境界を供給してから終了します。

通常ランタイムの正常shutdown・処理失敗時にも確定状態をログとレコーダーへ保存します。Dropによる強制停止では保証しません。
レコーダーは `paper_settlement`、`paper_delay_assumption`、`paper_event` を保存します。
約定の成立時刻・取引IDは `OrderFilled.trade` に残り、通知時刻は確定を実行した記録コンテキストの時刻です。
明示的な境界をランナー外で供給するとき、入力に由来する境界なら記録コンテキストも呼び出し元で接続してください。
IDの重複検出履歴と未確定取引は、正確性のため期間中保持します。長期運用ではメモリ量も監視し、
未確定状態を捨てて正常終了に見せるローテーションはしないでください。

## 価格・数量モデルと制約

価格優先・同価格では注文ID順に、公開約定の数量を上限として執行し、注文価格で代金・maker手数料を計算します。
注文はすべて板に残るmaker指値として扱い、板を横切るtaker約定は再現しません。
取引所とローカルの時計差は推定・補正しません。板時刻の下限で観測済みの板以前の取引による新注文の約定を防ぎますが、
送信・受付時間や時計差を完全には再現できません。キュー順位、受付・取消遅延の分布、市場インパクトも対象外です。

`tests/paper_settlement.rs` は固定の注文操作・開始残高に対し、通知遅延と順序だけを変え、
約定数量・代金・手数料・評価損益・共通の約定後価格列での値動きを比較します。
これは合成時系列による回帰検証です。実履歴での性能やpaper tradingの発生頻度の実測ではありません。
