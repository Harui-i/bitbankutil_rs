# paper tradingの約定モデルと時計

`PaperExecutionEngine::new(config, clock, balances, recorder)` で時計を明示します。
paper tradingでは `PaperClock::Realtime`、backtestでは `PaperClock::Replay { now_ms: 0 }` を選びます。
レコーダーは任意であり、記録用のtask-local contextも約定判定には使いません。

`Realtime` は発注受付時にシステムのUTC Unixミリ秒を読みます。
`Replay` は指定した時刻だけを使い、実行マシンの現在時刻や処理速度を参照しません。
`BotRunner::process` / `advance_time` は `TradingVenue::advance_replay_time` を通じて時計を更新します。
エンジンやvenueを直接使う場合は、呼び出し元が入力・注文操作の前に
`advance_replay_time(time_ms)` を呼んでください。再生時計の初期値は最初の入力時刻以下にします。
逆行する再生時刻と、実時計に対する再生時計更新は `InvalidClock` エラーになります。

時刻は次のように区別します。

- 受信時刻は市場データがローカルへ届いた時刻です。offlineでは記録の `received_at_micros` です。
- 戦略の実行時刻は `ctx.now_ms()` です。paper tradingでは実時計、offlineでは入力の受信時刻をmsへ切り捨てた再生時計です。派生イベントでも同じ再生時刻を使います。
- 取引所時刻は板の `last_timestamp()` や公開約定の `executed_at` です。ローカル時計と同じUTC epochを仮定します。
- 注文の有効開始時刻は、受付時の時計、既に観測した対象pairの板時刻、過去の注文有効開始時刻の最大値です。`OrderAccepted.effective_after_ms` に保持・記録します。

公開約定は、価格・方向が適合し、かつ `executed_at > effective_after_ms` の注文だけを執行します。
時刻精度がmsのため、同じms内の取引と注文の前後関係は確定できません。
保守的に同一msの取引は対象外とし、次のmsから対象にします。
例えば板の公開が1100ms、受付が1110msなら、遅れて届いた1000msの取引も1110msの取引も約定には使わず、1111ms以降の取引を使います。
1メッセージに古い取引と新しい取引が混在しても個別に判定します。

部分約定後も有効開始時刻を維持します。全約定・取消ではその注文の情報を破棄し、再発注では新たに時刻を計算します。
価格優先・同価格では注文ID順に、公開約定の数量を上限として執行します。
注文はすべて板に残るmaker指値として扱い、板を横切るtaker約定は再現しません。

取引所とローカルの時計差は推定・補正しません。板時刻の下限により、ローカル時計が遅れていても
観測済みの板以前の取引が新しい注文に適用されるのを防ぎます。
ただし板観測後の送信・受付時間や時計差を完全には再現できません。
取引所時計が進んでいる場合には現実には受付前の取引が対象になり得て、ローカル時計が進んでいる場合には約定を過小評価し得ます。
実時計の逆行や古い板によって下限は戻りません。時計差、キュー順位、受付・取消遅延の分布、市場インパクトはモデルの対象外です。

offlineでも入力全体を取引所時刻で並べ替えません。受信順で市場データを適用してから戦略を実行するため、
遅延した取引を除外しても、未来に受信する情報を戦略に与えることはありません。
